# SSH host identity checks

Before authenticating, the native app compares the server's public host key with the user's `~/.ssh/known_hosts` and the `known_hosts` file in ShellCanvas's app-data directory (beside `hosts.json`). Each file is parsed from one bounded snapshot. A conflicting or invalid policy in either file blocks the connection; an app approval cannot override the user's revocation or mismatch. It never authenticates first and verifies later. Standalone core probes use only the user's file unless the caller explicitly supplies an additional trust store.

Supported entries follow the [OpenSSH known_hosts format](https://man.openbsd.org/sshd.8#SSH_KNOWN_HOSTS_FILE_FORMAT): plain hostnames/IP addresses, comma-separated aliases, `*`/`?` patterns, negated patterns, hashed names, and bracketed endpoints for nondefault ports (including IPv6). Hostname matching is ASCII case-insensitive. Whitespace-separated fields, leading whitespace and comments are accepted. Host input must be a hostname or unbracketed IP address; host-pattern syntax is not accepted as a connection destination.

- Any matching, explicitly recorded raw public key is sufficient, unless that same key is revoked by a matching `@revoked` line. Revocation wins regardless of line order.
- A host with recorded raw keys but no matching offered key is a mismatch, including when the offered algorithm differs. It cannot be classified as a new host.
- Unrelated revocation and certificate-authority entries no longer disable the entire file. A matching `@cert-authority` entry alone does not authorize a raw key. Hosts requiring certificate verification still fail, and offered host certificates remain unsupported. A separately recorded matching raw key can be used alongside a CA entry.
- A missing file or absence of a matching entry produces the internal `Unknown` classification. Only a key unknown to both stores can enter the review flow; nothing is accepted or saved automatically.
- Unreadable, non-UTF-8, oversized (over 4 MiB), malformed or unsupported entries cause an error, even if another entry would match. This is a deliberate fail-closed restriction; it does not claim every OpenSSH syntax/version is supported. Individual noncomment lines are limited to 64 KiB.

System-wide host files, `HostKeyAlias`, `CanonicalizeHostname`, CA verification, SSHFP/DNS verification and key rotation through `UpdateHostKeys` are not implemented. ShellCanvas does not rewrite the user's file or remove obsolete entries from either store. Key fingerprints are not sufficient evidence of trust unless checked against an independently trusted source.

## New-host review

The first SSH handshake returns a typed unknown-key candidate without sending authentication. Native code retains the actual public key and issues a one-use random token, bound to that connection attempt, with a five-minute expiry. The frontend sees the endpoint, algorithm and SHA-256 fingerprint. Copying the fingerprint is available; approval stays disabled until the user acknowledges checking it through a trusted source. Cancellation is initially focused. Closing the dialog, Escape, a failed attempt or expiry releases the pending review. Late decisions cannot approve another attempt.

On explicit approval, the native backend locks its app-owned store, rechecks both trust files, and atomically persists the exact endpoint/key. Conflicting, revoked or malformed records are preserved and cause failure. Concurrent app writers preserve each other's records. The lock coordinates ShellCanvas writers; external tools editing the files do not participate in that lock.

A second SSH handshake verifies the current trust policy **and** requires the exact approved key retained in memory. A changed key fails without a second prompt, even if a trust file was edited to accept it. Only then can key/password authentication start. The same remembered endpoint can connect later without another review. Approval is durable independently of authentication: an approved key can remain saved if authentication fails or cancellation arrives after the authorized store write begins. Cancellation before approval saves nothing.

No replacement/removal UI or automatic key rotation is included. SSH agent, keyboard-interactive authentication and credential storage policy remain separate work.

## Verification

Tests cover plain/wildcard/negated/hashed entries, aliases, ports, IPv6, whitespace, multiple permitted keys, mismatches, revocation order, unrelated markers, CA-only refusal, malformed entries, invalid endpoints and file bounds. Local generated-key SSH servers additionally check unknown/changed/revoked/malformed cases in either trust store before authentication, known/user/app-trusted cases through authentication, and rejection of a different reviewed key despite a matching current trust file. They bind only to loopback, use temporary known_hosts fixtures and an in-memory generated host key, and never alter the user's real trust file or credentials.

The 2026-09-08 run passed 38 Rust tests and all-target Clippy. The additional alias and different-key-algorithm cases passed in the focused host-key suite. The authorized read-only evtinsait regression passed existing known-host verification, key authentication, Linux inspection, SFTP locations/preview, PTY input/resize and disconnect. HMAC/SHA-1 for hashed hostname matching and the test RNG reuse dependency versions already present through russh; no new package versions remain in the lockfile.

The enrollment checkpoint passed 43 frontend tests, 41 Rust tests, production frontend build, all-target Clippy and the standard Windows debug build. The authorized evtinsait read-only SSH/SFTP/PTY regression also passed after the connection changes. Native unit tests cover token ownership, one-use/expiry/cancel cleanup, exact port persistence, duplicate approval, concurrent writes and preservation of conflicting/corrupt files. Bridge tests cover missing/rejecting reviewers, endpoint mismatch, failed review and late approval after cancellation/expiry. The synthetic `tests/fixtures/host-trust.html` browser flow passed fingerprint copying, disabled/default-focus controls, rejection, Escape cancellation, approval, remembered reconnect, changed/revoked refusal, expiry recovery and key change after review. Its 1280×720 review panel fits without scrolling. Browser tests use fake trust and credentials; they do not prove native IPC enrollment or OS clipboard access. A full native enrollment walkthrough remains unverified.
